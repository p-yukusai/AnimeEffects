<!--
  Export destination table — DESIGN PROTOTYPE.

  This is the data asset the export UI is built from: every destination is a row
  that resolves to (container, codec, constraints, capabilities). It is DATA and
  not code because every fact in it moves — Discord moved GIF -> WebP, Twitch
  emote specs change, Safari's VP9-alpha support is in flight. Adding or
  correcting a destination must be an edit here, never a code change.

  Attributes:
    id          stable key, dotted: <platform>.<family>
    icon        icon file stem in assets/icons (no extension), resolved through the
                theme's tinting pass so it takes a theme colour like every other
                glyph. See assets/icons/README.md for provenance and licence.
    label       user-facing name (the thing they recognize)
    group       the section this row is listed under in the destination picker,
                keyed into the <groups> block above. The grouping axis is the
                PLATFORM a person is posting to ("telegram"), because that is the
                one thing they know before they start; `general` for the rows that
                have no platform of their own.
                NOT the family: that axis puts 29 of these 55 rows in one block and
                mixes what a file IS (sticker) with what it is FOR (post).
    family      sticker | chat | post | overlay | file | archive
                WHAT KIND of handover this is, which is what decides how hard to
                optimise for compatibility (and what the search field can match):
                sticker  a sticker or emoji for a chat app
                chat     sending a file in a conversation (an "attachment")
                post     uploading to a platform's feed or video host
                overlay  video that must keep its transparency (streaming, embedding)
                file     a generic deliverable: a file, a website
                archive  a master to keep
    artifact    what the destination produces. Default (absent) is a muxed video.
                still    ONE image file: the illustration case. `container` names
                         the image format (png, jpg) because there is no container
                         to mux, and the file goes to the name the user typed.
                sequence a directory of numbered stills (pixiv ugoira). The plan
                         applies maxFrames, so a 601-frame range becomes the 150
                         stills the platform accepts.
    fps         absent (default) | ignored. `ignored` means the export's frame rate
                does not reach the file at all, so the form does not ask for one:
                pixiv ugoira is a folder of numbered stills whose TIMING is authored
                on the upload page. The frame COUNT still applies (maxFrames).
    class       fixed    - the destination dictates the codec (most rows)
                reencode - platform re-encodes our upload (YouTube, X, TikTok)
                direct   - platform serves our file as-is (website, messaging)
                archive  - keep a master
    codecSelect fixed  - use @codec
                ladder - pick by (class, quality bucket) via the availability probe
    alpha/audio/loop
                required   - forced on; stated in the UI, never a control
                forbidden  - impossible or rejected; stated or hidden
                default-on / default-off - pre-set checkbox, overridable
                choice     - a real user decision
    checked     ISO date the facts below were last verified
    source      primary source for the facts
    verified    "true" only when checked against that primary source
    platform    any (default) | apple | windows | linux — rows whose codec only
                exists on one OS must say so, so validation can skip them

  Size modes:
    free          the destination imposes no size: the export dialog's own
                  Width/Height apply (they start at the project size)
    exact         exactly w x h. The art cannot match every aspect, so the remainder
                  is PADDED with transparency (`fit="crop"` crops instead, for a row
                  whose platform forbids margins). Every exact row here pads: Discord
                  requires a square canvas, WhatsApp recommends a stroke, Signal asks
                  for a margin, and WeChat's own pipeline crops over-spec art, so a
                  transparent margin is either required or accepted by all of them.
                  Crop exists for the row that will need it (LINE-style "no margins"
                  specs), and the table test asserts that an exact rule NEVER silently
                  stretches the art.
    max           fit inside w x h, preserve aspect
    maxExactSide  long side == @side, short side <= @side
    maxMinSide    fit inside w x h, then ensure long side >= @side

  <caps>          hard limits; 0 = unlimited. max* are ceilings (applied: the
                  plan trims frames, lowers fps or fits the file); minDurationSec
                  and minFrames are floors, which cannot be met by exporting less,
                  so they are stated rather than applied.
  <encOptions>    private encoder options (avcodec_open2). e.g. libvpx's
                  auto-alt-ref=0, which VP9+alpha requires.
  <codecTag>      four-char stream codec tag. NOT an encoder option — it lives
                  in the container's stream entry (hvc1 for HEVC).
  <audio>         per-destination audio parameters. Empty codec = derive from
                  the container (WebM cannot carry AAC).
  minScalePct     floor for fit-to-cap's scale phase (never shrink past this).
-->

  <!-- ===== groups: the picker's sections =============================
       A group is the PLATFORM a person is posting to: the one thing they know
       before they start, and therefore the axis the destination list is grouped
       by. A destination names its group with @group, and the order here IS the
       order of the sections on screen: `general` first, because the rows with no
       platform of their own are the honest answer for someone who has not decided
       (and the conservative floor, a 720p MP4 every chat app accepts, is then the
       row a fresh install has selected), then the platforms alphabetically.

       Titles are SHORT names, not labels: the row underneath already says what
       it makes ("Telegram sticker"), so the section only has to say where. A
       group with no rows is not drawn, and a row whose group is not declared
       here still appears, under its own key, at the end.

       @variants (default true) says the rows here are VARIANTS of one platform,
       so the picker draws the platform as a section you OPEN, with the
       destinations inside it. `variants="false"` means the rows merely share the
       absence of a platform - they are not alternatives to each other - so they
       are listed directly, and a platform with a single destination is listed
       directly for the same reason: a level of hierarchy that asks nothing is a
       click for nothing. -->

  <!-- ===== where each quality intent STARTS, within a codec's [best, worst] ==

       Without this the Quality selector was inert for every destination whose
       codec is FIXED (ten of these fourteen rows): the bucket picked the codec
       only when the codec came from the ladder, so "Smaller file" and "Best
       quality" produced byte-identical instructions for Telegram, Discord,
       WhatsApp or LINE. The bucket now sets the codec's own quality knob, and
       this is where its starting point is declared.

       position 0 = the codec's best value, 1 = the lowest we accept before the
       fit-to-cap loop gives up on quality and starts shrinking the image
       instead. ONE table for every codec, because the intent is about the trade
       the user is willing to make, not about a particular encoder — and a
       position rather than a CRF, because the numbers themselves are per-codec
       and already declared above.

       Policy, not fact: these are the numbers to tune, so they are data.
  -->
  <bucket_positions>
    <bucket name="smaller"  position="0.70"/>
    <bucket name="balanced" position="0.25"/>
    <bucket name="best"     position="0.00"/>
    <bucket name="lossless" position="0.00"/>
  </bucket_positions>
